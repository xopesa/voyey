## А. Результат и выбранный безопасный вариант

Реализован разрешённый пунктом 7.6 задания вариант: **проверяемая подготовка групп
и неисполняемый атомарный план**, без сохранения новых заказов. Это не включённый
split checkout и не завершённая транзакция создания двух Order.

Причина — финансовый блокер в текущем коде:

- `modules/checkout/domain.ts:prepareOrderItems` рассчитывает общие 50%.
- `d1/repositories.ts:priceD1Order` повторяет 50% после промокода;
  `writeD1Order` создаёт AWAITING_PREPAYMENT и резервирует конечный stock каждой строки.
- `modules/orders/status-policy.ts:submissionPhase/currentPaymentPhase` открывает
  оплату этого состояния; нет состояния неподтверждённого финансового draft.
- Существующий Payment approval переводит заказ в закупочный lifecycle, который
  требует отдельного решения для IN_STOCK. SQL Order требует ненулевые финансовые
  поля и согласованный requiredPrepayment/remainingAmount.

Сохранить новые Order со старыми 50% нельзя. Сохранить нулевые фиктивные суммы/
оплаченные состояния или добавить новые платёжные правила сейчас также запрещено.
Поэтому новые финансовые записи и статусы не создаются вообще. Существующие
инварианты не ослаблялись. Новые Order/OrderItem модели и миграция 0021 не нужны
до утверждения сохраняемого финансового контракта в 2.4; 0001–0020 не менялись.

## Группы корзины и план

GET /api/cart и ответы прежних операций дополнены `groups.IN_STOCK` и
`groups.PREORDER`: items, quantity, subtotal, checkoutEnabled=false. Пустая группа
имеет пустой список/нули. Старые items/subtotal/идентификаторы сохранены; Cart одна.
Добавлен hasLegacyItems. Наличие LEGACY не скрывается из общей корзины и не
преобразуется автоматически в новый режим.

Новый `modules/checkout/split-plan.ts`:

- `buildSplitCheckoutPlan`: чистая подготовка; сначала отклоняет LEGACY, включая
  смешение со свежими режимами. Проверяет уникальность SKU+mode, общий лимит SKU,
  активность, permission, конечный stock IN_STOCK и мерки по политике категории.
- Для каждого присутствующего нового режима создаёт одну **планируемую** группу
  с отдельным plannedOrderId, saleMode, subtotal и историческими снимками строк.
  Один SKU в двух режимах остаётся двумя разными строками/группами.
- Общий checkoutGroupId детерминирован по userId+key+version операции. Это ID
  предложения, не сохранённая сущность/ссылка на существующий Order.
- Сохраняет намерение reserve только IN_STOCK: variantId, quantity, expectedStock;
  у PREORDER inventoryReservedQuantity=0. Текущий stock при подготовке не изменяется.
- Содержит consumeCartItemIds и последовательность будущего единого guarded
  D1 commit: claim idempotency, повторная валидация, запись всех групп/снимков,
  reserve IN_STOCK, один discount accounting/audit, удаление выбранных строк.
  Это описание плана, не SQL executor.
- В плане нет payment status, requiredPrepayment, paidAmount или требований оплаты.
  Общий snapshotCheckoutLine извлечён из прежнего domain engine без копирования
  расчёта 50%; LEGACY engine по-прежнему использует его и свою прежнюю финансовую логику.

`SplitCheckoutPlanner.prepare` по умолчанию выключен. Explicit constructor opt-in
разрешает только подготовку для внутренних/изолированных проверок. HTTP route,
публичного env toggle и подключения к Worker/Manual API нет. `commit()` безусловно
выбрасывает 503 даже при opt-in. Чистая функция плана не умеет писать в БД.
COMMERCE_ENABLED=0, VOYEY_LOCAL_ONLY=1 сохранены; уведомления не создаются.

## Согласованность, ключи и пределы гарантий

Внутренняя prepare использует существующий D1 atomic/CAS для согласованного чтения
пользователя/корзины/каталога. Guard/cleanup — служебные кратковременные записи;
Order/Payment/Audit/CartItem/stock она не меняет. Заблокированный пользователь,
старый Order с тем же ключом для этого пользователя или несовместимая корзина
не дают подготовить предложение.

Повторная подготовка неизменной корзины тем же ключом даёт тот же план. Изменение
цены/характеристик даёт другой requestFingerprint при том же planned group ID.
Это **не durable idempotent replay созданного оформления**: ни группа, ни ключ
в БД не сохраняются. Сравнение fingerprint и конфликт несовместимого повторного
оформления должны быть реализованы на durable CheckoutGroup в 2.4. Полученный
план нельзя позднее исполнять без новой проверки текущей revision/корзины.

Два параллельных плана последней единицы могут быть валидны: подготовка её не
резервирует. Гарантии отсутствия oversell при создании новых связанных Order
появятся только с исполнителем одной D1 транзакции. Старые legacy stock races,
idempotency, rollback, snapshots, промокоды и manual orders прошли регрессию.

Ошибка создания второго нового заказа и откат первого **не тестировались как
реальное создание**: сохранение обоих отсутствует/заблокировано. Нет имитации
этой гарантии через поочерёдные записи, mock orders или фиктивные платежи.
В этом этапе вместо этого проверено нулевое количество новых бизнес-записей
при подготовке, отказах и любых попытках commit.

## Скидки — предложение без активации

`proposeDiscountAllocation` не подключён к promo redemption или checkout.
Предложение: вычислить скидку **один раз на всё оформление** прежним quote engine,
затем распределить пропорционально суммам групп методом наибольших остатков.
Целые расчёты BigInt исключают float ошибки; равные остатки разрешаются по ключу
группы, сумма долей точно равна исходной скидке. Отрицательные/дробные/избыточные
скидки и повторяющиеся ключи отвергаются. Для нулевой суммы допустима только скидка 0.
Это проверенный алгоритм предложения, но не утверждённая политика применения
лимитов промокода/доставки. Никакой redemption/скидки новым заказам не записано.
