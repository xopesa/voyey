## А. Motion

В `apps/miniapp/package.json` добавлена единственная прямая зависимость `motion` с точной версией **14.6.0**. `pnpm-lock.yaml` содержит её и штатные транзитивные `framer-motion`, `motion-dom`, `motion-utils`; отдельная конкурирующая анимационная библиотека не устанавливалась. React в установленном lockfile — **19.3.0**, Vite — **7.3.1**. Peer dependencies Motion допускают React/React DOM 18 или 19. `pnpm install --frozen-lockfile` прошёл.

Использованы официальные React API `motion`, `AnimatePresence`, `LayoutGroup`, `MotionConfig`, `useReducedMotion`, `useIsPresent`. Конфигурация соответствует [документации React Motion](https://motion.dev/docs/react), включая [MotionConfig](https://motion.dev/docs/react-motion-config) и [useReducedMotion](https://motion.dev/docs/react-use-reduced-motion).

`src/voyey/motion.tsx` задаёт общую систему:

| Действие                     | Настройка                                                 |
| ---------------------------- | --------------------------------------------------------- |
| Press                        | 120 ms, небольшое уменьшение масштаба                     |
| Вкладки и активный индикатор | 240 ms; мягкая spring, bounce 0.03                        |
| Страница                     | 260 ms; fade и смещение 6 px                              |
| Уход страницы                | 120 ms; fade и смещение 3 px                              |
| Диалог                       | 240 ms; fade и небольшое смещение                         |
| Выдача чека                  | 620 ms                                                    |
| Reduced motion               | Короткая opacity 80 ms; без пространственного перемещения |

Основные переходы страниц обёрнуты в `AnimatePresence mode="popLayout"`; `VoyeyPage` передаёт ref и делает уходящий контент `inert`/`aria-hidden`, чтобы он не принимал повторные действия во время fade. Постоянный App Shell, BottomNav и portal host не анимируются вместе со страницей. URL `voyey-demo.html?screen=...` сохранён; добавлены локальные экраны `order`/`receipt`, параметр `document=SETTLEMENT` и история модальных `panel`.

Микровзаимодействия реализованы в `components.tsx`: кнопки, heart state, лёгкое появление карточек без массового stagger, количество и цены, shared indicator режима корзины, галерея через opacity, native dialog с Motion enter/exit. Удалены прежние CSS press/hover transforms и CSS spinner animation, конкурировавшие с Motion. CSS остаётся источником оформления и статических состояний; градиентов нет.

Modal сохраняет native focus trap через `showModal()`, закрытие Escape и возврат фокуса к существующему исходному элементу. Back закрывает модальную запись истории, обычная навигация учитывает локальную глубину history и не добавляет повтор текущего URL. Эти обработчики проверены кодом/typecheck; полноценная браузерная проверка быстрых нажатий, Back и Escape после последних изменений не завершена.

`MotionConfig` учитывает системную настройку. В demo-профиле дополнительно предусмотрен переключатель «Уменьшить движение», который действует только в памяти запуска и не отключает системное ограничение. SSR-тест проверяет, что reduced receipt сразу содержит готовые действия без `translateY(-24px)`; реальное переключение в браузере и системное media preference на устройстве не проверены.

Контрольный размер отдельного minified ESM-модуля с используемыми экспортами Motion, с React external: **142 425 bytes**, gzip **48 464 bytes**. Это отдельное измерение библиотечных экспортов, не размер всего Demo. Новая библиотека не импортируется production entry; production Mini App JS/CSS имеют прежние имена и SHA-256. ## Б. BottomNav и фиксированная покупательская панель

В UI-01 `VoyeyBottomNav` уже находился вне переключаемого содержимого. Поэтому утверждать, что исходный дефект обязательно был remount, было бы неправильно. По исходному CSS выявлены две причины возможных сдвигов: высота задавалась только через `min-height`, подписи могли занимать разное количество строк; отсутствие постоянного scrollbar gutter позволяло менять доступную ширину при переходе между длинной и короткой страницей.

Исправления:

- `html` сохраняет вертикальную scrollbar-дорожку через `overflow-y: scroll` и `scrollbar-gutter: stable`; документ не сужается при появлении длинного контента.
- Панель имеет фиксированные height/min-height/max-height **78 px**, неизменные padding, ширину и bottom safe-area offset.
- У всех пяти пунктов одинаковая фиксированная высота, одинаковые размеры иконки и зарезервированная область подписи на две строки. Выбор пункта не меняет font-size или геометрию.
- Активная подсветка — абсолютный `motion.span layoutId="active"` внутри постоянного `LayoutGroup id="voyey-navigation"`; меняется только индикатор, не размеры кнопок. При reduced motion shared перемещение не используется.
- Бар остаётся постоянным sibling страниц и `AnimatePresence`, содержит стабильный React `useId` для проверки экземпляра.
- `VoyeyPurchasePortal` выводит фиксированный buy bar в `#vy-purchase-slot` вне анимируемой страницы. Transform страницы больше не может стать содержащим блоком fixed-панели.
- Buy bar имеет фиксированную высоту **64 px** и отдельный нижний отступ: bottom nav + nav height + gap **10 px** + safe area.
- На узком экране при фокусе текстового поля обе панели скрываются целиком по единому правилу. При уменьшении visualViewport учитывается клавиатура и выполняется аккуратное раскрытие поля в видимой области. Панели не перемещаются хаотично поверх клавиатуры. Обработчики и animation frame удаляются при размонтировании.

**Фактический результат до отключения браузера:** 35 последовательных переходов между Главной, Каталогом, Избранным, Корзиной и Профилем на размерах 320×844, 375×844, 390×844, 430×844, 768×844, 1280×844 и landscape 844×390. В каждой группе bounding rectangle совпал точно; один DOM instance `_r_2_` сохранился во всех переходах; высота 78 px; горизонтальное переполнение 0. Измерения сохранены в `docs/ui-02/nav-geometry-ru.json` и повторно проверены локальным скриптом.

Например, при viewport 390×844: x=12, y=756, width=351, height=78; доступная ширина страницы 375 из-за классического scrollbar 15 px. На 320×844: x=12, y=756, width=281, height=78.

Это подтверждает постоянство геометрии в проверенных обычных переходах RU. Измерения не доказывают плавность каждого промежуточного кадра, работу клавиатуры, поведение после scroll или отсутствие наложений buy bar на телефоне; эти браузерные сценарии остались непроверенными.

## В. Фирменный чек и mock-платежи

Новые файлы `ReceiptScreen.tsx` и `receipt.ts` реализуют:

- `VoyeyReceiptScreen` — экран компактного принтера и выдаваемой бумаги.
- `VoyeyReceiptPaper` — содержимое документа из конкретного заказа.
- `VoyeyOrderDetails` — путь «Профиль → Демо-заказы → Детали заказа → Чек», переход к оплате и отдельные FIRST/итоговые документы.
- `receiptFor()` — восстановление документа только из checkout snapshot и подтверждённых mock payment snapshots.
- `recordDemoArrival()` / `confirmDemoFinal()` — явно помеченный локальный simulator поступления/CARGO/FINAL, без Backend и реального финансового журнала.

### Слои и анимация

Корпус принтера светло-серый, с тонкой прорезью и красным индикатором. `vy-printer-body` расположен выше бумаги по z-index; `vy-print-window` ограничивает её видимую область. `motion.article` раскрывается через `clipPath` и небольшое перемещение `y: -24 → 0` за 620 ms. Высота документа не анимируется, текст не масштабируется. После завершения появляются save/share actions. При reduced motion готовая бумага появляется через короткую opacity. Экспорт строится отдельно из данных, поэтому не захватывает промежуточный кадр.

Оформление использует палитру и исходный логотип VOYEY UI-01, белую бумагу, пунктирные разделители, мягкие тени и зелёный статус только подтверждённого платежа. Логотип и изображения не изменены. Отдельного изображения принтерного референса в доступном текущем сообщении не было; принтер реализован по текстовому описанию, без заявления о точном визуальном совпадении с недоступным изображением.

### Источники данных и ограничения

При submit в claim сохраняется точная сумма `order.firstAmount`. При mock APPROVED создаётся отдельный frontend snapshot `DemoConfirmedPayment`: id, phase, amount, submittedAt, confirmedAt. Pending/rejected не записывают подтверждённые деньги. Это память Demo, не Backend PaymentLedger.

`receiptFor()` требует одновременно подходящие APPROVED claim и payment snapshot с совпадающими id, суммой и временем; проверяет положительные целые деньги, состав/количество, скидку, FIRST 50/100 и согласованность итогов. Наличие только исторического APPROVED без нового подтверждённого snapshot не создаёт документ. Изменение текущего каталога не подменяет сохранённые название, вариант, цену, количество или характеристики заказа. Чужие заказы в документ не объединяются.

На бумаге выводятся логотип, информационная/demo-пометка, номер `DEMO-...`, дата подтверждения в Asia/Tashkent, saleMode, товары/варианты/количество/цены, subtotal, promo при наличии, discount, goodsTotal, подтверждённая сумма, остаток и CARGO. Имя, телефон, адрес покупателя и выбранный файл чека не экспортируются. Налоговых реквизитов, фискального QR и выдуманного номера реального заказа нет.

Внизу: «Спасибо за покупку в VOYEY!» и «Информационное подтверждение оплаты. Не является фискальным чеком» — с RU/UZ переводом.

| Состояние                               | Результат                                                                                                   |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Нет платежа / истёк без подтверждения   | Документ недоступен                                                                                         |
| SUBMITTED                               | «Чек отправлен на проверку», сумма, время подачи и попытка; подтверждённого чека нет                        |
| REJECTED                                | Отказ и допустимая повторная подача; подтверждённого чека нет                                               |
| IN_STOCK FIRST100 APPROVED              | «Оплачено», вся стоимость товаров после скидки, остаток 0                                                   |
| PREORDER FIRST50 APPROVED               | «Предоплата подтверждена», половина с округлением вверх, остаток товаров, CARGO неизвестен                  |
| PREORDER FIRST100 APPROVED              | Товары оплачены полностью, но CARGO неизвестен; итоговый расчёт не объявляется завершённым                  |
| Поступление + подтверждённый mock FINAL | Отдельный итоговый документ: FIRST/FINAL, фактический CARGO, полная сумма, остаток 0, «Расчёт завершён»     |
| FIRST100 + фактический CARGO0           | Simulator закрывает расчёт без второго нулевого платежа; подтверждённый FIRST остаётся единственной оплатой |

Пример автоматической проверки PREORDER50: товары 72 000, FIRST 36 000, CARGO 17 000 после поступления, FINAL 53 000, итог 89 000. Для FIRST100 + CARGO10 000: FIRST 72 000, FINAL только 10 000. Сценарий нечётной суммы 101 даёт FIRST 51 и остаток 50. Исторический документ FIRST остаётся неизменным после поступления/FINAL; итоговый документ открывается отдельно.

Правила FIRST UI-01 сохранены: 24 часа, максимум три принятые попытки, replay без расхода попытки, pending до решения, одно 2h окно после подходящего позднего отказа. Серверные правила 2.5B2 не менялись. Данные живут только в памяти текущего запуска; навигация не удаляет `state.orders`, reload сбрасывает демонстрацию.

## Г. Экспорт PNG и Share

`receipt-export.ts` реализует Canvas-рендерер без дополнительного пакета и внешних сервисов:

1. Ожидает локальный font и декодирование оригинального PNG логотипа.
2. Использует тот же `ReceiptData` и `receiptAmounts()`, что React-бумага.
3. Рисует только белую бумагу шириной 360 CSS px с разрешением 2×, логотипом, текстом, разделителями и суммами. Длинные названия/подписи переносятся по измеренной ширине.
4. Создаёт `image/png` через `canvas.toBlob` и локальное скачивание `VOYEY-DEMO-...-FIRST.png` либо `...-SETTLEMENT.png`.
5. Для Share проверяет наличие `navigator.share`, `canShare({files})`; при отсутствии поддержки или ошибке использует скачивание. Отмена системного Share не запускает нежелательное скачивание. Blob URL освобождается.

Принтер, bottom bar, поля ввода и controls в PNG не входят. Источник — статический снимок данных, а не animated DOM или screenshot. Нельзя экспортировать pending/rejected как подтверждённую оплату; UI передаёт только результат `receiptFor()`. Ошибки Canvas/font/image/PNG показываются через RU/UZ toast. Экспорт имеет synchronous lock от двойного запуска, блокирует только собственные действия и не блокирует навигацию.

**Подтверждено автоматическими тестами:** draw commands используют сохранённые суммы и оригинальный logo source, RU/UZ переносы, отказ Canvas, save/download ветка, unsupported/throwing canShare fallback, успешная native-share ветка, cancel без download, fallback после ошибки Share.

**Не подтверждено в настоящем браузере:** реальное PNG-кодирование и скачанный файл, его визуальная читаемость/цвет/сохранение логотипа, вызов системного меню Share и поведение конкретного WebView. В тестах Canvas/Share APIs имитируются; тестовый Blob не выдаётся за фактически скачанный чек. Web Share также зависит от secure context, возможностей устройства и user activation; после async encoding отдельные браузеры могут потребовать fallback. PDF не добавлялся.
