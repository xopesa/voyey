## Реализованная модель

Активная архитектура сохранена: Worker → Fastify → D1 repositories → D1/SQLite.
Prisma schema используется для описания моделей и генерации типов; PostgreSQL
runtime и исторические PostgreSQL миграции не активировались.

- `Category.attributeDefinitions`: JSON-массив описаний характеристик, default `[]`.
- `Product.attributes`: JSON-объект значений товара, default `{}`.
- `ProductVariant.attributes`: JSON-объект значений SKU, default `{}`.
- Определение: `key`, `nameRu`, `nameUz`, `type`, `scope`; для чисел опциональны
  `unit`, `min`, `max`. Типы: `TEXT`, `NUMBER`, `INTEGER`, `BOOLEAN`.
- `scope=PRODUCT` по умолчанию; `VARIANT` задаёт характеристику SKU.
  Категории свободные, без enum из трёх названий.
- Все характеристики необязательны. Рост/вес покупателя не являются требованием
  новой модели. Никакие реальные категории или товары не создавались.

| Пример категории  | Product.attributes                          | ProductVariant.attributes                  | Прежние поля SKU                               |
| ----------------- | ------------------------------------------- | ------------------------------------------ | ---------------------------------------------- |
| Одежда            | `material: "cotton"`                        | Дополнительные значения по схеме категории | `size: "M"`, `color: "blue"`                   |
| Канцтовары        | `brand: "Fixture"`                          | `pack_count: 12` (INTEGER, unit=шт)        | Цвет может быть заполнен, размер отсутствовать |
| Средства ухода    | `purpose: "cleaning"`, `composition: "..."` | `volume: 250.5` (NUMBER, unit=ml)          | Размер/цвет могут отсутствовать                |
| Будущие категории | Произвольные разрешённые ключи              | Произвольные разрешённые ключи             | SKU сохраняется обязательным                   |

Это примеры тестовых данных, а не бизнес-классификатор. В частности, состав —
обычная текстовая характеристика, без добавления косметической классификации.

Размер остаётся строкой в БД/DTO/снимке OrderItem. API создания варианта допускает
отсутствие `size`, `null`, пустую или пробельную строку и сохраняет отсутствие как
`""`. PATCH `size: null` очищает размер; отсутствие size в PATCH сохраняет его.
`availableSizes` не включает пустые значения. Старые непустые размеры не изменены.
Цвет сохраняет прежний nullable контракт: отсутствие при создании даёт `null`.
Прямой SQL INSERT без size по-прежнему не поддерживается старым NOT NULL полем;
нормализация выполняется поддерживаемым API/repository.

Цена, валюта, акция и себестоимость остались на Product. Цена SKU не добавлена.
SKU, stock, images, size/color, isActive и `preorderEnabled` сохранены. Генератор
SKU по размеру/цвету работает по-прежнему: не переписывает атрибуты существующих
вариантов, новым задаются пустые атрибуты через SQL default.

## Валидация и целостность

Реализация: [shared normalizers](C:/Users/USER/Desktop/Voyey/packages/shared/src/catalog-attributes.ts),
[API schemas](C:/Users/USER/Desktop/Voyey/apps/api/src/modules/admin/catalog/schemas.ts),
[category compatibility](C:/Users/USER/Desktop/Voyey/apps/api/src/modules/admin/catalog/attributes.ts),
[D1AdminCatalogRepository](C:/Users/USER/Desktop/Voyey/apps/api/src/d1/repositories.ts).

- До 32 определений и до 32 значений в объекте; максимум 16 KiB UTF-8 на JSON.
  Ключи — lower_snake_case, до 50 символов; подписи RU/UZ — до 200 символов,
  unit — до 30, текстовые значения — до 2000.
- Значения только скалярные. Вложенные объекты/массивы, null, NaN/Infinity,
  небезопасные числа, неверные типы/границы, неизвестные ключи/поля отклоняются.
  Строки обрезаются по краям; текст не может быть пустым. Числовой coercion отсутствует.
- Зарезервированы встроенные поля SKU/size/color/stock/price и prototype-ключи.
  Характеристики не подменяют цену, остаток или встроенный размер/цвет.
- На активном D1 create/update проверяют соответствие категории внутри `atomic()`.
  Изменение схемы категории проверяет все её товары и варианты, включая архивные.
  Удаление используемого ключа, несовместимые тип/границы/область/единицы → HTTP 409.
  Допустимы совместимые подписи, новые необязательные поля и удаление неиспользуемых.
- Перемещение товара проверяет его значения и все SKU против целевой схемы.
  Несовместимость или переинтерпретация используемых единиц → HTTP 400.
  Значения не удаляются автоматически.
- PATCH `attributes` заменяет весь объект; `{}` очищает. Отсутствие поля сохраняет
  значения. Изменения и AuditLog атомарны; аудит сохраняет ключи, без значений.
- Проверен конфликт конкурентных изменений схемы/товара и откат записи при ошибке
  AuditLog. Использован существующий D1 Batch/CAS, без изменения механизма транзакций.
- SQL CHECK защищает форму JSON и размер. Согласованность с категорией обеспечивает
  активный API/repository; прямое SQL-редактирование может обойти эту проверку.

## Checkout и следующий этап — только план

В [checkout/domain.ts](C:/Users/USER/Desktop/Voyey/apps/api/src/modules/checkout/domain.ts:39)
каждая строка по-прежнему требует целочисленные heightCm 100–250 и weightKg 30–300.
Проверка не зависит от категории, size/color или новых attributes. CartItem/OrderItem
допускают null в БД, но checkout отклоняет неполные мерки. Каталог сам их не требует.

Интеграционный тест: товар без размера/цвета добавляется в корзину без мерок;
checkout возвращает 409, не создаёт Order и не уменьшает stock. При добавлении
мерок проходит прежний сценарий с 50% предоплатой и AWAITING_PREPAYMENT.
Передавать фиктивные рост/вес для реальных покупателей не предлагается.

Для следующего этапа потребуется отдельно согласовать:

1. Явную политику мерок для одежды и остальных категорий, правила смешанной корзины,
   валидацию backend и формы UI. Не выводить необходимость мерок из наличия size.
2. Снимок выбранных характеристик/единиц в OrderItem, чтобы изменения каталога
   не меняли смысл оформленного заказа. Сейчас новые attributes туда не копируются.
3. Контракт выбора IN_STOCK/PREORDER, резервирования и оплаты 50%/100% — отдельно
   от характеристик каталога и только после согласования финансовых правил.
4. Представление новых характеристик/отсутствующего размера в Admin, Mini App и
   Telegram. Текущий channel publisher требует непустой латинский размер и не готов
   публиковать generic SKU без размера (`telegram-channel/publisher.ts:123`).

Эти изменения не выполнялись. `PREORDER.checkoutEnabled=false`; явный saleMode
по-прежнему отвергается строгими checkout/cart/manual-order schemas. stock=0
не обходится флагом preorderEnabled. stock=null сохраняет legacy unlimited смысл.
Предоплата ceil(total/2), ручная карта → приватный чек → решение администратора,
финальная оплата, CARGO, отмены/возвраты и финансовые суммы не менялись.

## Ограничения реализации

Все новые характеристики optional, без enum-значений, массивов, вложенных структур,
required-полей, наследования или локализации самих значений. Локализованы подписи.
Категории остаются плоскими. Нет фильтрации/индексов/поиска по новым JSON-полям.
Проверка редактирования схемы читает все товары/SKU категории, включая архивные;
её стоимость растёт с каталогом и потребует измерений перед масштабированием.
Frontend не редактирует/не отображает новые характеристики. Этот этап готовит
Backend, но не завершает пользовательский путь покупки универсальных товаров.
